## prompt_library_versus_production_site_archive

Superdesign's own discovery path starts with reusable design *directions*. Its README shows `superdesign search-prompts --query "<keyword>"` or `--tags "style"`, followed by `superdesign get-prompts --slugs "<slugs>"` and `get-prompts --slugs "<slug>" --full`. For a specific existing website, `superdesign extract-website --url https://example.com --design-md` extracts design DNA; the CLI also documents flags for brand, tokens, content structure, and cloning. The project's persistent design-system location is `.superdesign/design-system.md`. These are prompt discovery, site extraction, and local product-context operations, not a searchable editorial corpus of production-site screenshots. [prompt_library_versus_production_site_archive[0]] [9]

Inspo instead starts from **real shipped websites**: its repository reports **832 sites**, **2,320 captured pages**, desktop and mobile captures, palettes, real fonts, detected technology, and a fold-by-fold autopsy. It also describes **68 canonical reference components** and a site-specific `DESIGN.md`. These archive entries are external examples to evaluate; they do not automatically become the current application's `.superdesign/design-system.md`. The filename similarity is especially easy to mistake for a shared file contract, but the two documents have different owners and purposes. [prompt_library_versus_production_site_archive[1]] [7][prompt_library_versus_production_site_archive[0]] [9]

A concrete Superdesign case illustrates the boundary. For an existing app, its documented path can create a project from a *before-state* replica HTML, then branch variations using `superdesign iterate-design-draft --draft-id <draftId> -p "..." --mode branch --context-file .superdesign/design-system.md`. The upstream instructions insist that the replica describe UI already present in the repository, not a redesigned page with invented placeholder sections. Inspo observations therefore belong in the subsequent variation brief, not in a falsified baseline replica. [prompt_library_versus_production_site_archive[0]] [9]

| Inspiration question | Appropriate upstream operation | Output to carry forward |
|---|---|---|
| "What design directions are available?" | Superdesign `search-prompts`, then `get-prompts`. [prompt_library_versus_production_site_archive[0]] [9] | A selected prompt direction, adapted to the user's product. |
| "What visual system does this specific website use?" | Superdesign `extract-website --url ... --design-md`. [prompt_library_versus_production_site_archive[0]] [9] | Extracted context to evaluate, not a mandate to clone. |

The practical distinction is **design instruction versus external evidence**. Preserve both, but never silently promote a reference site's branding into the application's own design system.

## a_bounded_research_first_order_with_anti_copy_constraints

Refero provides the clearest published sequencing rule. Its skill says research must precede implementation, then asks for **3-5 different visual search angles**: a broad aesthetic, a category or domain, and, when relevant, a strong product. It retrieves **3-4 full styles**, compares their contributions, selects **one primary foundation**, and borrows **1-2 specific details** from others. For more complex product work, it separates styles, screens, and flows; its pre-implementation decision ledger records each major choice, its source, and why it applies. This is a precedent for making the agent *decide* rather than merely collect screenshots. [a_bounded_research_first_order_with_anti_copy_constraints[0]] [5]

Inspo supplies a complementary shortcut, not the same fixed budget. Its official MCP page describes choosing one of **19 named macrostructures** before writing code and finding production examples of that shape; `recommend(brief)` composes a macrostructure choice, **five exemplars**, matching reference components, and a palette. The documentation also describes four real production sites illustrating a chosen shape. Those figures describe particular tool outputs or site guidance, not an injunction to call every Inspo tool or to implement all five examples. A sensible bridge could start with one `recommend` call, inspect one or two useful screens in depth, and broaden only if the brief is still ambiguous; that last sentence is a *proposed budget*, not an official Inspo rule. [a_bounded_research_first_order_with_anti_copy_constraints[1]] [8][a_bounded_research_first_order_with_anti_copy_constraints[2]] [10]

Refero's anti-copy instruction is explicit: **do not copy one reference**; synthesize several into a direction for the user's product, preserve a dominant reference's useful traits rather than averaging everything, and describe the result as a new direction rather than "copying X." Its reference lock records **3-5 traits** to preserve and **1-2** secondary details to borrow. The Inspo material reviewed presents examples, screenshots, and reference JSX, but does **not** specify an equally explicit prohibition on copying brands or prose. Consequently, a bridge's rule to exclude names, logos, page copy, distinctive imagery, and ornamental signature treatments should be identified as *proposed orchestration policy*, informed by Refero and by the difference between learning from a site and reproducing it. [a_bounded_research_first_order_with_anti_copy_constraints[0]] [5][a_bounded_research_first_order_with_anti_copy_constraints[2]] [10]

The revealing contrast is between Inspo's convenience and Refero's discipline. A five-example recommendation makes reference retrieval cheap; without a selection and transformation step, that convenience can increase imitation or context sprawl. Require a short, source-linked decision ledger before any canvas iteration.

## a_thin_contract_from_inspo_evidence_to_superdesign_drafts

A proposed skill could trigger on an explicit request to **design or redesign a UI with real-site inspiration** when both the Superdesign skill/CLI and nutlope's Inspo MCP are available. It should not intercept unrelated coding or generic screenshot requests. Cursor and Claude can load project-level skills, but a bridge should remain an additional instruction file, not a fork of either upstream repository. Superdesign's README already gives different installation paths for coding agents and Claude Code; in Claude Code it cautions against installing both its plugin and `npx skills add` copy. [a_thin_contract_from_inspo_evidence_to_superdesign_drafts[0]] [12][a_thin_contract_from_inspo_evidence_to_superdesign_drafts[1]] [13][a_thin_contract_from_inspo_evidence_to_superdesign_drafts[2]] [9]

Its operation could be specified as a short sequence:

1. **Frame the user's task and constraints**: existing versus new page, audience, required sections, existing product identity, accessibility, and whether outside inspiration is wanted. Consult the repository's current design system before changing it. [a_thin_contract_from_inspo_evidence_to_superdesign_drafts[2]] [9]
2. **Research with Inspo**: call `recommend(brief)` first, narrow with `search_screens` or `find_examples_for_macrostructure`, and inspect selected `get_screen(slug)` and `get_design_system(slug, live?)` results. `find_similar` and `find_by_color` can answer a specific unresolved structural or palette question; `find_reference_components` and `get_reference_jsx` are optional aids, not required imports. [a_thin_contract_from_inspo_evidence_to_superdesign_drafts[3]] [10]
3. **Write a compact evidence packet**: for each selected reference, record its source **URL or archive identity**, macrostructure and page type, palette roles and useful colors, font family/type hierarchy, and fold-by-fold hierarchy or "fold autopsy". Add the *transferable lesson*, the product-specific adaptation, and an explicit "do not copy" note. Inspo documents the underlying site captures, fonts, palettes, and fold analysis; this packet format is the proposed bridge contract. [a_thin_contract_from_inspo_evidence_to_superdesign_drafts[4]] [7][a_thin_contract_from_inspo_evidence_to_superdesign_drafts[3]] [10]
4. **Hand off to Superdesign**, rather than generating a competing draft: preserve the existing `.superdesign/design-system.md` unless the user has requested a change; give the research packet as a concise design brief or variation prompt; then let the Superdesign skill manage `create-project`, `iterate-design-draft --mode branch --context-file .superdesign/design-system.md`, review on the returned canvas/preview URL, and optional `get-design` export. [a_thin_contract_from_inspo_evidence_to_superdesign_drafts[2]] [9][a_thin_contract_from_inspo_evidence_to_superdesign_drafts[5]] [3]

The boundary rule is specific: **transfer layout logic, information hierarchy, spacing, palette *roles*, and typography *principles***; do not transfer a reference site's brand identity, logo, written copy, proprietary imagery, distinctive decoration, or entire JSX as the user's finished product. `get_reference_jsx` provides a component example, not evidence that the example is authorized as the new application's branding or content. This is recommended integration design, not an upstream-documented joint workflow. ## failure_modes_in_a_shared_agent_session

**Competing installations and triggers.** Superdesign explicitly warns Claude Code users not to install its plugin and also install the unnamespaced `npx skills add` version: that creates a second copy. Adding a bridge with an overbroad "design anything" trigger can further make it unclear which instructions govern a task. Give the bridge a narrow research-plus-handoff trigger and leave `/superdesign:superdesign` or the installed upstream Superdesign invocation intact. The trigger-collision risk is an inference; the duplicate-install warning is documented. [failure_modes_in_a_shared_agent_session[0]] [9]

**Context and provenance loss.** Refero notes that full styles are large enough to merit batching, while Inspo's `recommend` already bundles examples, components, palette, and evidence. Loading many full site design systems, screenshots, JSX files, and Superdesign context into the same request could obscure which source justifies a decision. Keep a bounded reference set and a source-to-decision ledger rather than pasting the archive wholesale. The context-loss mechanism is an integration inference, grounded in the documented payload shapes and Refero's batching warning. [failure_modes_in_a_shared_agent_session[1]] [5][failure_modes_in_a_shared_agent_session[2]] [10]

**Wrong baseline or wrong authority.** Superdesign requires its existing-page replica to show the *before* state, while its design-system file expresses local project context. Treating an Inspo page as that replica, replacing local tokens with a reference site's `DESIGN.md`, or pasting reference JSX directly into production collapses research into copying. Preserve the product baseline, use references only in the iteration brief, and seek user approval for brand-level changes. [failure_modes_in_a_shared_agent_session[0]] [9][failure_modes_in_a_shared_agent_session[3]] [7][failure_modes_in_a_shared_agent_session[2]] [10]

**External fetches and partial failures.** Superdesign's skill instructs a single retry if `extract-website` fails or times out, then continuing without extraction where possible; it also limits retries for failed draft commands. Inspo's live design-system extraction fetches source HTML and CSS server-side without executing JavaScript, while its MCP is read-only. Consequently, a live extraction may not explain client-rendered details, and a temporary extraction failure should not be treated as a successful design-system handoff. The client-rendering limitation is an inference from the documented no-JavaScript behavior. [failure_modes_in_a_shared_agent_session[4]] [3][failure_modes_in_a_shared_agent_session[2]] [10]

## synthesis

The three public projects differ in **mechanism, scope, and authority**. Inspo supplies read-only evidence from shipped sites, including structure and visual measurements; Refero demonstrates how an agent can turn multiple references into a deliberate, non-copying design decision; Superdesign owns local product context, canvas drafts, iteration, and export. Inspo's reference `DESIGN.md` and Superdesign's `.superdesign/design-system.md` are therefore not substitutes, even though their names invite confusion. [synthesis[0]] [7][synthesis[1]] [5][synthesis[2]] [9][synthesis[3]] [10]

The useful integration is not "more inspiration in the prompt." It is an **evidence-to-brief handoff**: use Inspo to identify and attribute a few relevant production patterns, apply Refero-like reference limits and anti-copy decisions, and ask the existing Superdesign workflow to explore those decisions on its canvas under the user's own identity. No public joint skill was confirmed in the materials examined; the contract above is a practical proposal for one. [synthesis[4]] [8][synthesis[1]] [5][synthesis[2]] [9]
